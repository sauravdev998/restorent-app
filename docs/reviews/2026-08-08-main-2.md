# Review, main, 2026-08-08 (second pass)

**Reviewed by**: Sonnet 5 (author on Opus)
**Scope**: 9 files, uncommitted (working tree vs `main` @ `fb20fd2`)
**Verdict**: Changes requested

## Summary

This is a fix set closing the three `/check verify` failures (health blocking 30s and returning a
bodiless 408, SSE headers not flushing for up to 15s, the Vite dev proxy hiding upstream death) and
two of the four majors from the prior review (the listener reconnect backoff that never reset, the
stream-status hook that couldn't tell a retry from a permanent failure). All five fixes are correct
for the scenario each was written against, and `/check verify` has already proven that at runtime.
Reading past the proven scenarios turned up two problems the app-driving verify pass wasn't set up to
catch: the Vite proxy's new `error` handler destroys the client response for *every* proxied `/api/*`
request, not just event streams, silently replacing Vite's own 502 diagnostic with a raw connection
reset for ordinary API calls whenever the backend is unreachable; and `PgListener::connect` still
carries SQLx's unmodified 30 second default `acquire_timeout` on its own internal pool, so each
individual reconnect attempt can block up to 30 seconds regardless of what the (now correctly
resetting) backoff delay says, which is largely why `verify.md` measured retries 31 seconds apart
while the delay itself said 1 and 2. Both are cheap, well-precedented fixes (the codebase already
has the exact pattern needed for each, just not applied here), which is why this lands at Changes
requested rather than Blocked.

## Major

### 🟠 The Vite proxy's `error` handler destroys the response for every `/api/*` request, not just event streams, `web/vite.config.ts:59-63`
**Problem**: The new `proxy.on('proxyRes', ...)` handler (the fix for the "API killed mid stream"
bug) correctly checks `content-type` before touching a response, exactly like its predecessor did.
The new `proxy.on('error', ...)` handler added right next to it, for the sibling case of a
connection that fails outright, has no such scoping — it runs for *any* proxied request that errors
at the connection level (`ECONNREFUSED`, `ECONNRESET`, a timeout), SSE or not, and unconditionally
calls `res.destroy()`. I confirmed the effect directly: `opts.configure` runs before Vite registers
its own default `proxy.on('error', ...)` handler (`node_modules/.../vite/dist/node/chunks/node.js`,
the call to `opts.configure(proxy, opts)` precedes `proxy.on("error", ...)`), and Node's
`EventEmitter` invokes listeners in registration order. A small reproduction using the same handler
ordering shows the sequence plainly: this handler's `res.destroy()` runs first, then Vite's own
handler runs and calls `res.writeHead(502, ...).end()` without throwing (so nothing crashes), but the
client never receives it — it gets `socket hang up` instead of Vite's diagnosable
`502 http proxy error: ...` page. Vite's own console log line still prints, but the browser side of
the diagnosis is gone.
**Why it matters**: This isn't scoped to the scenario the comment describes ("a stream that fails
rather than closing"). It fires for *every* `/api/*` request proxied while the backend is down or
restarting — which, given the project is 20-odd features from done and the API will be started and
stopped constantly during that work, is an extremely common local-dev state. Every ordinary
`fetch('/api/...')` made in that window now shows a bare connection error in the browser instead of
Vite's normal, actionable 502, for the rest of the project's local development.
**Suggested fix**: Scope this handler the same way its sibling is scoped — check `_req.url` (or track
which requests are event-stream requests) before destroying `res`, so only `/api/events` connections
get the aggressive treatment and ordinary API calls keep Vite's default error page.

### 🟠 `PgListener::connect`'s own pool keeps SQLx's 30 second default acquire timeout, so each reconnect attempt can still take 30 seconds regardless of the backoff delay, `api/src/infrastructure/events/listener.rs:144`
**Problem**: `Backoff` now resets correctly — that part of the fix is solid and well tested. But the
delay `Backoff` computes (1s, 2s, 4s, ... up to 30s) is only the *wait between* attempts;
`connect_and_listen` awaits `PgListener::connect(database_url).await?` for the attempt itself, and
that call is unbounded by anything this diff touches. Reading `sqlx-postgres`'s `PgListener::connect`
(`~/.cargo/registry/.../sqlx-postgres-0.9.0/src/listener.rs:43-57`): it builds its own
`PoolOptions::<Postgres>::new().max_connections(1)...` with no `.acquire_timeout(...)` override, so
it inherits `sqlx-core`'s default of `Duration::from_secs(30)`
(`sqlx-core-0.9.0/src/pool/options.rs:160`). The new `ACQUIRE_TIMEOUT` constant in
`api/src/infrastructure/db/mod.rs` is applied only to the unrelated `Database::pool`; the listener's
internal pool never sees it.
**Why it matters**: This is already visible in this run's own `verify.md` ("Extra evidence from the
second run"): retry log lines during a real outage were measured 31 seconds apart while the delay
itself said 1 and then 2. That's not the backoff ladder working as designed — the reported delay is a
rounding error on top of a ~30 second floor every single attempt pays regardless of the ladder's
current value. The whole point of this diff's listener change was to make recovery fast after a brief
blip; as shipped, a brief blip still costs roughly 30 seconds to notice, because the connect attempt
itself dominates. The fix is real (the reset bug is gone, and that matters for long outages where the
ladder would otherwise stay pinned at 30s), but its benefit for the common case — a short blip — is
mostly theoretical until the attempt itself is bounded.
**Suggested fix**: Wrap `PgListener::connect(database_url).await?` in `tokio::time::timeout`, the
exact pattern already used for `Database::is_reachable` a few files over, bounded comfortably under
`RECONNECT_DELAY_MAX` (30s) so a hung attempt doesn't itself become the bottleneck.

## Minor

### 🟡 The new timeout-ordering test duplicates literals instead of referencing the real values it claims to guard, `api/src/infrastructure/db/mod.rs:176-188`
**Problem**: `the_database_waits_are_shorter_than_the_timeouts_around_them` declares its own local
`REQUEST_TIMEOUT = 30s` and `HEALTH_CHECK_TIMEOUT = 5s` and asserts the module's real constants are
smaller than those copies. The actual router timeout lives in `api/src/presentation/router.rs:21`
(`const REQUEST_TIMEOUT: Duration = Duration::from_secs(30)`, currently private) and the actual
health-check timeouts live in `infra/lib/platform-stack.ts` (both the ECS container check and the ALB
target group check use `Duration.seconds(5)`). All three currently agree, but nothing makes them keep
agreeing — this test only checks that `ACQUIRE_TIMEOUT`/`HEALTH_PROBE_TIMEOUT` are smaller than
*copies* of those numbers, not the numbers themselves. Change `router::REQUEST_TIMEOUT` to 10s and
this test is still green while the original bug (the router racing the pool's wait) is back.
**Why it matters**: the four layer, dependencies-point-inward rule means `infrastructure` genuinely
cannot import a constant from `presentation` to fix this cleanly, so this is a real constraint, not
an oversight — but it does mean the test's name overstates what it verifies.
**Suggested fix**: At minimum, note in the test's doc comment that it only pins the *relationship*
between this module's own two constants and doesn't verify agreement with `router.rs` or the CDK
stack, so a future reader doesn't mistake it for the cross module guarantee it reads like.

### 🟡 Cutting the pool's acquire timeout from 30s to 5s applies to every request, not just health, `api/src/infrastructure/db/mod.rs:29,75`
**Problem**: `ACQUIRE_TIMEOUT` is set on `PgPoolOptions` itself, so it bounds every
`self.pool.begin()` call across the app, not only the health probe (which has its own, tighter
`HEALTH_PROBE_TIMEOUT` wrapper and would never actually reach the pool's 5s limit — 2s always fires
first). That's a deliberate and reasonable choice for the outage case the doc comment describes, but
it also means legitimate pool contention — the spec's own named risk, "a single heavy or badly
indexed query starves connections for every other restaurant mid service" — now fails a
`begin_scoped` caller after 5 seconds instead of 30, before there's any real traffic to know whether
5s has headroom for it.
**Why it matters**: Not a bug — failing fast is arguably the better default — but it's a production
behavior change riding in on what reads like a narrowly-scoped health-check fix, with no discussion
of the trade-off for ordinary request handling once real load exists.
**Suggested fix**: No change needed now; worth a one-line note in the doc comment that this bound
applies pool-wide, and revisiting the value once `max_connections` is sized against real concurrency.

### 🟡 The system status panel still reads stale "Up" values while the API is dead, contradicting the (now-correct) stream badge on the same screen, `web/src/app/system-status.tsx:20` (not touched by this diff)
**Problem**: Called out directly in this run's own `verify.md`: with the API process dead, the
stream badge this diff fixed now correctly reads `Closed`, but `system-status.tsx`'s
`useQuery(healthQuery)` panel keeps showing the last successful `Database Up` / `Live updates
listener Up` reading, because TanStack Query holds prior data with no visible error state on a failed
refetch.
**Why it matters**: Not a regression from this diff — the file isn't in the change set — but this
diff makes the contrast sharper: the same screen now shows one indicator that correctly reports the
outage and one that doesn't, right next to each other.
**Suggested fix**: None owed by this change; flagging so it isn't lost before real kitchen screens
depend on this panel. `useQuery`'s `isError`/`isStale` state (or a short `staleTime`) is enough to
stop showing a green reading for data that's minutes old.

## Strengths

- The `Infallible` return type on `connect_and_listen` plus `Ok(never) => match never {}` is the
  right fix, not just a working one: it makes the exact prior bug (a reset sitting in a match arm
  that could never run) impossible to reintroduce by construction, because the compiler now refuses
  a version of this function that returns success without going through the one path that resets the
  backoff. That's a direct, well-aimed response to the previous review's suggested fix.
- Extracting `Backoff` into its own small, pure, testable type is exactly what the prior review asked
  for ("expose something more testable"), and the two new tests genuinely exercise it: ceiling
  behavior under 100 repeated failures, and the specific regression (delay pinned at the ceiling
  after a long outage, reset back to the short wait on reconnect).
- `use-live-events.test.tsx`'s `ControllableEventSource` models the real WHATWG distinction correctly
  (`CONNECTING` during a browser-managed retry vs `CLOSED` on a fatal response) and the regression
  test is written against the actual prior bug with a clear comment explaining why "closed" beats
  "connecting" for staff watching the badge.
- `Database::is_reachable`'s `tokio::time::timeout` wrap is correct and its doc comment's claim that
  dropping the future frees the pool waiter (so repeated probes don't pile up) is exactly what
  `verify.md` measured (three probes during an outage, each ~2.00s, no growth).
- The `proxyRes` handler in `vite.config.ts` is correctly scoped to `text/event-stream` responses
  only, mirroring the pre-existing content-type check — a useful contrast with its unscoped sibling
  above.

## Test coverage

Test signal is `configured`. Rust: 8/8 unit tests pass (`cargo test`), including the two new
`Backoff` tests and the new timeout-ordering test. Web: 5/5 Vitest tests pass, including the three
new `useLiveEvents` tests. `cargo clippy -- -D warnings`, `cargo fmt --check`, `pnpm exec eslint`, and
`pnpm exec tsc --noEmit` are all clean on the changed files (re-run directly as part of this review,
not only taken on `verify.md`'s word).

What's covered well: both structural fixes this diff set out to make (`Backoff`'s reset, and
`useLiveEvents`'s `readyState` branching) now have tests that encode the actual prior bug as the
regression case, not just a happy path.

What's untested, and inherently hard to unit test the way this diff is structured: the two Major
findings above. The `PgListener::connect` timeout gap lives in a dependency's default, not in code
this crate's test suite touches; the Vite proxy's error-handler ordering is a Node `EventEmitter`
registration-order effect that only shows up by running two proxied requests against a stopped
backend and inspecting what the browser actually receives — outside what `cargo test`/Vitest
exercise, and outside what `/check verify`'s scenarios (which drove the SSE path, not an ordinary
JSON call) happened to hit.
