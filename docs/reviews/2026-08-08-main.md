# Review, main, 2026-08-08

**Reviewed by**: Sonnet 5 (author on Opus)
**Scope**: 80 reviewable files (of 87 changed), branch-equivalent vs `eeaf143` (`git diff eeaf143 HEAD`)
**Verdict**: Changes requested

## Summary

This is a greenfield scaffold: a four-layer Rust/Axum API, a React/Vite web app, and an AWS CDK
stack, built to spec 0001. The structural core is genuinely good — the tenant-scoping type
(`ScopedTx`, a private pool, a module handlers cannot import) really does make an unscoped query a
compile error, the domain/application layers are honestly free of `axum`/`sqlx`, and the
owner/`app_api` role split matches the spec's "the owner bypasses RLS" warning exactly. `/check
verify` already ran and correctly caught three real bugs (health blocking 30s, SSE headers not
flushing for up to 15s, the dev proxy hiding upstream death) — those are not repeated here. This
review found four additional, un-reported problems: a reconnect backoff that never resets after
its first climb, a stream-status hook that lies forever once `EventSource` gives up for good, an
ALB security group that is open to the whole internet on port 80 (bypassing CloudFront), and zero
automated coverage on the single most load-bearing piece of code in the change, the scoped
transaction. None of these are exploitable as data leaks today (no tenant tables exist yet, no
sessions exist yet), which is why this lands at Changes requested rather than Blocked, but two of
the four (the backoff and the ALB rule) are cheap to fix now and expensive to debug later once real
traffic exists.

## Major

### 🟠 Postgres listener reconnect delay never resets after its first climb, `api/src/infrastructure/events/listener.rs:57-84`
**Problem**: `spawn()` loops calling `connect_and_listen`, resetting `delay` back to `RECONNECT_DELAY`
(1s) only on the `Ok(())` arm of the match (line 62). But `connect_and_listen` (line 87) can only
ever return via `?` propagating an `Err` — its inner `loop` (line 98) has no `break` or `return`,
it either keeps forwarding notifications or exits by propagating a `try_recv`/`connect`/`listen`
error. `Ok(())` is therefore unreachable, and the reset line never runs.
**Why it matters**: Once the connection has failed enough times in a row to push `delay` up to the
30 second ceiling, it stays at 30 seconds for the rest of the process's life, even after the
listener has been solidly connected for days. A brief blip during deploy (a handful of failed
reconnects while RDS is between maintenance states, for example) permanently degrades this
instance's recovery time from "back in ~1-2s" to "back in ~30s" for every future outage, silently,
with nothing in the logs calling out that the backoff is stuck at its ceiling. Given the listener
is what makes an instance deliver anything at all (`close_all()` fires and `/api/health` goes
unhealthy while it's down), a slower recovery here directly extends how long the kitchen goes dark
per incident.
**Suggested fix**: Reset `delay` at the top of each successful `connect_and_listen` call (e.g. reset
it right after `alive.store(true, ...)` inside `connect_and_listen`, or have `spawn` reset `delay`
whenever `alive` transitions to `true`, not only when the function returns `Ok`). Either way, the
reset condition needs to be "we are connected now," not "the function returned Ok," since it never
does.

### 🟠 The live-stream status hook cannot distinguish "retrying" from "gave up for good," `web/src/shared/events/use-live-events.ts:62-66`
**Problem**: `source.onerror` unconditionally sets `status` to `'connecting'`, on the stated
assumption that "EventSource reconnects on its own." That is true for a genuine network blip
mid-stream, but per the SSE spec (and both major browser implementations), a non-2xx response —
such as the 401 `/api/events` currently returns for every request outside development, and will
keep returning for every request with no valid session until feature 7 ships — causes the browser
to *fail the connection permanently*: `readyState` goes to `CLOSED` and no further reconnect is
attempted. The hook never reads `source.readyState`, so it cannot tell these two cases apart.
**Why it matters**: Deploy this scaffold today and every browser that loads it will show
"Connecting" in the header forever, implying a retry is in progress, when the stream has actually
died for good and nothing will bring it back short of a page reload. That is worse than showing
"Closed," because "Connecting" tells staff to wait rather than to reload. The same failure mode
recurs later for any *real* fatal cause (a revoked session, a bad restaurant id) once feature 7
lands the real auth, so this isn't only a today-problem.
**Suggested fix**: In `onerror`, check `source.readyState === EventSource.CLOSED` and set a distinct
terminal status (or reuse `'closed'`) rather than `'connecting'` in that case; reserve `'connecting'`
for `readyState === EventSource.CONNECTING`.

### 🟠 The load balancer accepts HTTP from the whole internet, bypassing CloudFront entirely, `infra/lib/platform-stack.ts:177`
**Problem**: `loadBalancer.addListener('Http', { port: 80, open: true })` creates a security group
rule allowing inbound TCP/80 from `0.0.0.0/0`. Confirmed by running `cdk synth`: the generated
template's ALB security group reads `CidrIp: 0.0.0.0/0, Description: Allow from anyone on port 80`.
Nothing in the stack restricts the ALB to traffic that actually came through CloudFront (no
CloudFront managed prefix list on the security group, no shared-secret header check at the origin).
**Why it matters**: The whole session/cookie design in spec 0001 leans on "one origin... the session
cookie simply works," implicitly assuming CloudFront is the only path in. As written, anyone who
learns the ALB's DNS name (trivial: `dig` any AWS account's ALBs, or it's in the CDK outputs) can
talk to the API directly over plaintext HTTP, skipping CloudFront's TLS termination, any future WAF
rule, and any edge-level rate limiting or caching protection. Today the practical blast radius is
small (no sessions exist yet, `/api/health` is meant to be public, dev routes are compiled out of
the production image), but this is exactly the kind of infrastructure default that is cheap to fix
now and a real exposure once feature 7's session cookies are live.
**Suggested fix**: Restrict the listener's security group to CloudFront's managed prefix list
(`com.amazonaws.global.cloudfront.origin-facing`) instead of `open: true`, or add a custom header
CloudFront injects and the ALB/app checks. Either is a small, well-documented CDK change.

### 🟠 The structural tenant-scoping mechanism has no automated test, `api/src/infrastructure/db/mod.rs`, `api/src/infrastructure/db/scoped.rs`
**Problem**: `Database::begin_scoped` (the function that issues `SET LOCAL app.restaurant_id`) and
`ScopedTx` are the entire enforcement mechanism the spec calls "structural, not a convention." Zero
automated tests exercise them — no repository-level test runs `begin_scoped` against a real
Postgres inside a rolled-back transaction, which is the exact pattern `AGENTS.md` prescribes for
this layer ("repositories are integration tested against a real Postgres inside a rolled back
transaction"). The only evidence this works is a manual curl walkthrough recorded in `verify.md`.
**Why it matters**: This is the single most security-relevant piece of code in the whole change —
per the spec, it's one of the two locks on "the most expensive thing to get wrong." A `docker
compose up -d` Postgres is already part of local dev, so nothing structural blocks writing this
test; it just hasn't been written yet, which the guide calls out explicitly as worth flagging when
a critical, security-relevant path is untested and easy to regress silently (e.g. someone "fixing" a
warning in `begin_scoped` and dropping the `SET LOCAL`, or swapping `true` for `false` and turning
it into session-wide `SET`, which would leak one request's restaurant into the next request on a
pooled connection with no test catching it).
**Suggested fix**: This is `/test`'s job, not something to fix in this review, but it should be the
first thing `/test` adds: an integration test that opens `begin_scoped`, asserts
`current_restaurant_id()` reads back the right value inside the transaction, and asserts it reads
back `NULL` on a fresh connection after commit (verify.md already proved this manually — turn it
into a test). A second test worth having: `RestaurantScope`'s fail-closed behavior outside
development, which today is only proven by the container image check in `verify.md`.

## Minor

### 🟡 The dev-only query parameter isn't URL-decoded, `api/src/presentation/extract/scoped.rs:87-92`
**Problem**: `query_value` splits the raw query string on `&` and `=` and returns the value verbatim,
without decoding `%`-escapes. Since a UUID never contains characters that need escaping, this
happens not to matter for the current use, but it's a landmine for whoever next reaches for this
helper and hands it something that does need decoding.
**Suggested fix**: Either delete this once feature 7 replaces the whole file (which is the stated
plan), or run the value through a minimal percent-decode if it survives longer than expected.

- ⚪ `infra/lib/platform-stack.ts:2513`, `imageTag` silently defaults to `'latest'` when the

  `cdk deploy` with no context would quietly deploy whatever `latest` currently points to.
- ⚪ `api/src/domain/error.rs:518-525`, `DomainError::Invalid`/`Conflict` messages go straight into
  the HTTP response body (`presentation/error.rs`). Nothing misuses this today, but there's no
  guard stopping a future caller from putting something internal in one of these strings — worth a
  comment at the definition site as a tripwire for whoever adds the next domain error.

## Strengths

- The tenant-scoping story is the real thing, not a comment promising it: `Database`'s `pool` field
  is private, `db::scoped` is the only way to get a connection, and `AppState` never exposes a raw
  pool to a handler. This was verified structurally (private field, module boundary) rather than
  taken on faith.
- `api/src/domain` and `api/src/application` are genuinely free of `axum`/`sqlx` imports — confirmed
  by reading every file, not just the module doc comments claiming it.
- `EventRegistry`'s test (`an_event_never_reaches_another_restaurants_stream`) is exactly the right
  test for the scariest risk in the spec, and it isn't a happy-path-only test — it also asserts the
  *other* restaurant's stream got nothing.
- `cargo check`, `cargo clippy -D warnings`, `cargo test`, `pnpm typecheck`, `pnpm lint`, and
  `cdk synth` were all re-run as part of this review and are clean, matching what `verify.md`
  reported.
- The CDK stack shows real judgement, not just translated YAML: no NAT gateway with a documented
  cost rationale, `deletionProtection`/`RemovalPolicy.RETAIN` on the database and the web bucket, the
  CloudFront-to-ALB `readTimeout` deliberately set above the 15s heartbeat, `FORCE`-aware role split
  reasoning carried into `init-roles.sql` down to the default-privileges grant so future migrations
  don't need their own grant statement.

## Test coverage

Test signal is `configured` (Vitest + `cargo test`, `/test` not yet run for this feature). Current
coverage: 5 Rust unit tests (config parsing, health composition, event registry isolation and
close-all) and 2 web tests (the dev restaurant-id placeholder). All pass.

What's covered well: the one thing this scaffold most needed proven — that an event for restaurant A
never reaches restaurant B's stream — has a real unit test, not just the manual curl check.

What's untested and should be first in line for `/test`, in priority order:
1. `Database::begin_scoped` / `ScopedTx` (see Major finding above) — needs a real-Postgres
   integration test per `AGENTS.md`'s own stated convention for this layer.
2. `use-live-events.ts` — the exact file with the `onerror`/`readyState` bug above has no test at
   all; a test asserting the hook's `status` transitions for a fake `EventSource` in each of
   `CONNECTING`/`OPEN`/`CLOSED` would have caught it.
3. The listener's reconnect backoff (see Major finding above) is inherently hard to unit test as
   written, because the reset logic is buried in an unreachable match arm — which is itself a sign
   the function should expose something more testable (e.g. return whether it reset cleanly, or take
   the backoff state as an injectable parameter) rather than a reason to skip testing it.
- `RestaurantScope`'s production fail-closed branch (`api/src/presentation/extract/scoped.rs`) has
  no Rust-level test; it's currently proven only by the container-image manual check in `verify.md`.
  Worth a lightweight test once there's a way to construct `Parts`/`AppState` cheaply in this crate.
