## Minor

### 🟡 New error-mapping wiring in `ErrorScreen` has no test, `web/src/app/error-screen.tsx:30`
**Problem**: The route error boundary now calls `apiErrorMessage(isRouteErrorResponse(error) ? error.data : undefined, t)` to render a translated sentence instead of nothing. `apiErrorMessage` itself is thoroughly tested, but there is no `error-screen.test.tsx` (none existed before this change either) exercising this component at all — not the `isRouteErrorResponse` branch, not the `error.data` shape, not that the sentence actually renders in the DOM.
**Why it matters**: This is currently dead in practice (no route in the app throws a `Response` yet — data comes from TanStack Query, not loaders), so the risk is low today, but it is new logic and, per the project's own convention, error-handling code is exactly the category the review guide weighs heaviest. The first loader that throws a `Response` shaped differently than `{ error, message }` (e.g. a bare fetch `Response` without a parsed JSON body) will exercise this path for the first time in production rather than in a test.
**Suggested fix**: Add a small `error-screen.test.tsx` that renders `ErrorScreen` inside a router configured to throw a representative `Response` with an API-shaped JSON body, and asserts the translated sentence appears. Cheap, and it turns this from "believed correct" into "proven correct" the same way the rest of this feature is.

## Strengths

- The catalogue-as-single-source-of-truth design is executed cleanly on both sides: the web app parses (never casts) `@catalogue`, the API validates the same file with `include_str!` at boot via `LazyLock`, and a malformed catalogue fails the boot rather than the first request on both sides. `catalog.rs`'s repository tests (`a_fresh_restaurant_takes_the_catalogue_defaults`, `the_defaults_match_the_column_defaults_in_migration_0003`) genuinely pin the migration's hard-coded defaults against the catalogue's, which is the exact kind of drift a naive implementation would miss.
- Test quality throughout is unusually high for the size of this change: `resolve.test.ts` exercises both resolvers against a matrix of restaurant/staff/localStorage/kitchen-surface combinations including the row a single shared resolver would get wrong; `format.test.tsx` checks Indian digit grouping, exact-decimal formatting (`9007199254740993.15`, which is not representable as a `double`), zero- and three-decimal currencies, and timezone divergence with two real IANA zones on opposite sides of the same instant; `error-message.test.ts` runs assertions through the real `t()` (in both English and Hindi) rather than a stub, specifically to catch a mapped key with no translation behind it.
- Accessibility is genuinely load-bearing, not decorative: `RestaurantText` correctly implements WCAG 2.2 Language of Parts (`lang` from the restaurant's language, `dir="auto"` from the text itself, never the reader's own language), and its test asserts against `container.textContent` rather than `getByText` specifically because the latter collapses whitespace and would hide a component that silently tidied up a restaurant-typed name.
- The Dockerfile's `WORKDIR /build/api` change and the `COPY locales /build/locales` step correctly account for `include_str!("../../../locales/catalogue.json")`'s relative-path resolution from `api/src/domain/language.rs` — I traced the path arithmetic by hand and it is exactly right, matching the depth-preserving comment above it.
- Money is handled correctly end to end: `formatMoney` takes the exact decimal *string* and formats it via `Intl.NumberFormat`'s string-input overload rather than parsing to a `number` first, which is what actually prevents the float-precision bug the code comments claim to prevent (verified with a value literally chosen to not be representable as an IEEE double).
